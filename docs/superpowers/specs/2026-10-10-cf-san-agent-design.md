# cf-san ASN Scanner Agent Design

**Status:** Approved by the user on 2026-10-11
**Date:** 2026-10-10  
**Repository branch:** `codex/ip-pool-worker`

## 1. Goal and scope

Extend the existing Cloudflare Worker + D1 IP pool with a Go scanner agent and a one-command installer. The agent scans only the current IPv4 prefixes originated by an ASN the operator is authorized to scan, tests TCP/443, identifies Cloudflare responses using the agreed HTTP check, and reports accepted records and durable scan progress to the existing backend.

This change includes:

- Worker/D1 APIs and schema for agent scan plans and checkpoints.
- A Go CLI/agent named `cf-san`, with a text menu and command-line flags.
- Debian and Alpine Linux installation support.
- GitHub Actions releases for Linux `amd64` and `arm64`.

It does not change the existing public `/postip` and `/getip` contracts, and it does not deploy the new version to production as part of implementation.

## 2. Confirmed behavior

- Scan only authorized, currently announced IPv4 prefixes for the selected ASN; do not expand the target scope to other ASNs or Cloudflare-wide ranges.
- Obtain originating prefixes from RIPEstat RIS Prefixes (`types=o`, `af=v4`, with noise filtering), sort prefixes numerically, then scan ascending blocks.
- Split prefixes into `/24` blocks. A prefix narrower than `/24` remains one smaller block. ZMap may permute addresses inside each block.
- Persist completion at block granularity. A pause or crash during a block leaves that block incomplete; the next run may rescan it. Completed blocks are not rescanned during the same plan.
- Finish one pass and stop. On a later run, refresh the ASN prefix plan and add new blocks. A withdrawn prefix is no longer scheduled; its history is retained.
- Region is parsed from `loc=` in the trace response. If the response has no usable `loc`, it is not accepted as a Cloudflare edge record and is not stored.
- Cloudflare result validation is case-insensitive `Server: cloudflare`, with the response body rejected when it contains `error code: 1034`. HTTP status alone does not disqualify a response. The probe path is `/cdn-cgi/trace` (single slash).
- A valid result is reported immediately. Progress is also reported every ten minutes and when a block completes. Invalid/non-Cloudflare results update progress only and never create an IP row.
- Use the existing WebUI-configured API Bearer token for agent endpoints. The API token and administrator password continue to follow the existing plaintext-in-D1 requirement.
- `--limit` means the ZMap initial TCP probe rate in packets per second (PPS), default 100; zero is rejected. ZGrab2 sender concurrency is a separate setting and menu item. The `--limit` value is not a total network-interface packet shaper for the subsequent TLS/HTTP traffic.
- Agent CLI flags include `--asn`, `--url`, `--token`, and `--limit`; CLI values override saved configuration. ZGrab2 sender count is also configurable in the menu and persisted locally.
- The installer command is generated by the authenticated WebUI and invokes the Worker-served `/install` script with `--url` and `--token`. The token is passed as a shell argument, not as a URL query parameter, and is saved locally with restrictive file permissions.

## 3. Worker and D1 design

### Scan-plan API

Add an API-token-protected endpoint:

- `GET /api/agent/v1/plan?asn=<number>`

The Worker fetches the current RIPEstat originating IPv4 prefix set for the ASN, rejects invalid or non-public prefixes, normalizes and sorts the complete prefix set, then returns it with sparse checkpoints. It must not materialize or persist one D1 row per `/24`: a large ASN may produce hundreds of thousands of scan blocks. The Go agent lazily merges the prefix ranges into the same numerically ordered `/24` blocks (keeping prefixes narrower than `/24` intact), preserving the existing target range and block ordering. If the live prefix source cannot be reached or validated, fail closed and do not start a new scan using an unverified target set.

The compact D1 state stores the latest checkpoint per source prefix. The agent resumes from the greatest completed block position across those sparse rows and repeats that block only when it was active. If the normalized live prefix set changes, reset the compact cursor so newly announced ranges below the prior cursor are not skipped. The legacy `scan_blocks` table is retained; migration copies its completed progress into sparse checkpoints without deleting its historical rows.

### Report/checkpoint API

Add an API-token-protected endpoint:

- `POST /api/agent/v1/report`

The request includes ASN, source prefix, block CIDR, progress state, and an optional candidate record. With no candidate, the Worker updates progress only. With a candidate, it verifies that ASN/port/region are valid and the IP belongs to the reported block, then atomically upserts the IP record and progress. The Worker trusts the agent's network observation; it validates data and scope but does not independently probe the target.

### D1 migration

The initial schema includes a legacy scan-block table keyed by `(asn, block_cidr)`, containing source prefix, active/completed state, latest accepted IP (informational only), last report time, and timestamps. The compact-plan migration adds an ASN prefix snapshot and sparse checkpoint table; it copies completed progress from the legacy table while leaving its historical rows intact. Existing `ip_records` and `app_settings` schemas and public route behavior remain unchanged.

## 4. Agent workflow

1. Load saved configuration and contact the Worker over HTTPS with the Bearer token. Fail before scanning if authentication, backend connectivity, ASN configuration, or plan retrieval fails.
2. Fetch and synchronize the current plan; process blocks in ascending numeric order.
3. For each block, run ZMap against TCP/443 with the configured `--limit`. Feed open-port results to ZGrab2 with the configured sender count for TLS/HTTP follow-up.
4. For candidates, issue a direct HTTPS GET to the IP at `/cdn-cgi/trace`. Certificate verification may be disabled only for this public IP probe; the agent's connection to its backend must use normal TLS verification and must never forward the API token to scan targets.
5. Apply the agreed header/body check, parse `loc=`, and immediately report only valid records with port `443`, the selected ASN, and the parsed region. Responses without `loc` are treated as non-qualifying and are not stored.
6. Send a heartbeat every ten minutes and a final block-completion report. Invalid probes never create records.
7. On pause or termination, stop dispatching new work and leave the active block incomplete so it is safely rescanned on resume.

Because ZMap permutes targets within a block and does not provide a reliable event for every non-responsive attempted address, the ten-minute heartbeat records the active block and the last completed block—not an exact latest attempted IP. This is consistent with the selected block-level checkpoint model; the active block may be repeated after interruption.

## 5. CLI, menu, and local configuration

`cf-san` opens a text menu with:

1. Initialize/check environment and backend connectivity.
2. Run scanning in the background.
3. Pause scanning gracefully.
4. Set ZMap rate (`--limit`, PPS).
5. Set ZGrab2 sender concurrency.
6. Set ASN.
7. Show backend/config/status and exit.

The local configuration stores backend URL, token, ASN, rate, sender count, and agent ID in a root-owned file with mode `0600`. Scanner state is primarily in D1; local state is for process control and resumable operation metadata. The menu starts and stops the agent process; no automatic boot-time service is required in the first version.

## 6. One-command installation

The authenticated admin UI provides a copyable command similar to:

```sh
curl -fsSL 'https://<worker-host>/install' | sudo bash -s -- \
  --url 'https://<worker-host>' --token '<api-token>'
```

`GET /install` serves the versioned installer script. The script detects Debian/Alpine and CPU architecture, installs or verifies ZMap/ZGrab2 prerequisites, downloads the matching `cf-san` release, writes protected configuration, and installs the command. It must fail with actionable diagnostics if the OS/architecture or dependency cannot be supported; it must not silently install an unpinned source build.

The generated command contains the API token by explicit product request. The WebUI must warn that copied commands can be retained in shell history and command-line arguments may be visible to local users. The token must not appear in the installer URL, URL query, or Worker logs.

## 7. Release and verification

GitHub Actions publishes reproducible Go binaries and checksums for Linux `amd64` and `arm64`. Installer compatibility is tested separately for Debian and Alpine, including dependency detection and permission handling.

Acceptance tests include:

- Worker plan/report API token auth, prefix synchronization, block ordering, and invalid-scope rejection.
- D1 migrations and atomic candidate+progress updates.
- Go unit tests for IPv4 range splitting, ascending block ordering, checkpoint resume, interruption/restart, `loc` parsing, and all supplied Cloudflare response cases.
- Mocked ZMap/ZGrab2 process tests for cancellation, rate/sender arguments, stdout pipeline, and ten-minute progress reporting.
- Installer shell tests for Debian/Alpine detection, architecture selection, token-safe handling, and unsupported-platform failure.
- GitHub Actions matrix build and artifact checksum verification.
